# Feature Specification: Proactive Leader Bot

**Feature Branch**: `002-proactive-leader-bot`
**Created**: 2026-05-11
**Status**: Draft
**Input**: User description: "I want our leader bots to be proactive so that I am not the leader as a player. I want to follow. So the leader bot has to take on the full leader role. It has to ping me like, come on, Tony, let's go, let's quest. It should communicate with me. It should ask me what I want to do next, whether I want a quest, whether I want to go to battleground or whether I want to go to some dungeon instance. So it can even try going somewhere, but it always should check whether I am near. So it doesn't go too far away. It should always check for me and ask, hey, come on, why are you standing? Let's go, let's play. So I want it to act like a real human and not wait for orders or commands from me, only approve approvals."

## Clarifications

### Session 2026-05-12 (analyze remediation)

- Q: A1 — should the new `Proactive.*Cooldown*Sec` keys subsume the existing tactical ambient caps, or should proactive emits also count against them? → A: **Also count against them.** FR-019 updated: proactive emits route through the existing `Tactical.AmbientMinSpeechGapSec` / `Tactical.AmbientMinEmoteGapSec` / `Tactical.AmbientMaxVisibleActionsPerMinute` counters via a single funnel (tasks.md T023a). A misbehaving proactive loop cannot exceed the module-wide spam budget.
- Q: A3 — `fallbackZone` candidate kind: leave it as a planning artifact or acknowledge it in the spec? → A: **Acknowledge in the spec.** FR-002 updated to allow a soft zone-suggestion as a fallback when the deterministic selector finds no quest/dungeon candidate. Preserves the user's "don't go silent on me" intent.
- Q: A10 — kill switch default direction (FR-018)? → A: **Default OFF.** FR-018 updated. Feature is opt-in so server operators get byte-identical baseline behavior unless they explicitly enable it.
- Q: A15 (implicit) — does FR-015's "offer an alternative" mean the bot must internally chain to a new proposal in the same tick, or wait for the next heartbeat? → A: **Next heartbeat.** FR-015 updated. Abort emits one chat line, then the existing tick-driven proposal cycle re-fires on the next heartbeat with the now-empty open-proposal slot.

### Session 2026-05-11

- Q: Battleground execution in v1 — keep BG as a proposable activity (and accept that BG-queue is likely a missing primitive) or drop it entirely from v1? → A: Drop battleground from v1 scope. v1 supports two activity categories: **quest** and **dungeon**. Existing playerbot primitives (`accept *`, `talk *`, travel/follow strategies, manual zone-in for instances) are sufficient — no new MCP verb required. Random Dungeon Finder / LFG queueing is explicitly NOT a v1 path; "dungeon" means a specific named instance the leader bot walks the player to and zones into.
- Q: How is "activity completed" detected so the bot auto-proposes the next one? → A: **Hybrid.** Per-category server signals are primary — quest = quest turn-in event, dungeon = zone-out from the instance map (or final-boss kill). Explicit player "done" / "next" / "what's next" chat command always works as a fallback that overrides any pending signal state. If neither signal nor explicit command arrives within a hard timeout (default ~30 min, configurable), the bot sends one chat nudge ("are we done with this one?") and, after a further short wait with no answer, marks the activity abandoned and returns to the proposal cycle.
- Q: How does the bot pick *which* specific quest or dungeon to propose? → A: **Player's quest log + current zone first, then expand outward.** Ranking order: (1) quests already in the player's quest log, preferring ones the player has made progress on or whose objectives are nearby; (2) quests offered by quest givers in the player's current zone that the player can accept and that match level + faction; (3) dungeons whose level range covers the player and whose entrance is reachable from the current zone; (4) fall back to a "next level-appropriate zone for this faction/race" candidate if everything above is exhausted. Selection is deterministic and reproducible — the LLM phrases the proposal, but does NOT choose the candidate. This keeps the proposal feeling like a real friend who actually looked at your log.
- Q: Which chat channel does the leader bot use for proactive lines (proposals / waiting / idle nudges)? → A: **Party-if-grouped, else whisper.** Never `/say` and never `/yell` for proactive lines. Proposals, waiting/proximity lines, and idle nudges all go to `/party` when the leader bot and the player share a group; otherwise they go to `/whisper` directed at the specific player character. Public chat (`/say`, `/yell`) is reserved for emergent in-world events handled by the existing tactical ambient path and is NOT used by this feature. The player's approval/rejection answers are parsed from the same channels the bot speaks on, plus the existing whisper/say capture path.
- Q: Audit logging — reuse the existing `mod_ollama_chat_gateway_audit` table or stand up a dedicated one? → A: **Reuse `mod_ollama_chat_gateway_audit`** with new `source_channel` labels for each lifecycle event (`proactive_proposal`, `proactive_approval`, `proactive_rejection`, `proactive_nudge`, `proactive_complete`, `proactive_abort`). No new SQL migration required for audit; the feature ships **without** a new module schema. Same prune path (`.ollama gateway prune`) applies.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Leader bot proposes an activity and waits for approval (Priority: P1)

When the player logs in or finishes the previous activity, the designated leader bot opens the conversation by suggesting a concrete next activity (a quest or a dungeon run — battleground is out of v1 scope) and asks the player to confirm. The bot does **not** start moving, accepting, or zoning anything until the player explicitly approves. If the player says no, the bot proposes a different option from the same menu. Only after explicit player approval (e.g. "ok let's go", "yes", "do it") does the bot trigger the corresponding playerbot action sequence.

**Why this priority**: This is the core inversion of the existing dynamic — today the human is the leader and the bots react to commands. Without this proposal/approval loop, none of the rest of the feature makes sense. It is also the smallest slice that delivers value on its own: even with no proximity logic and no idle nudge, a bot that opens with "Wanna do Wailing Caverns?" and waits for "yes" already changes the play experience.

**Independent Test**: Player logs in next to the gateway leader bot. Within a short window (single-digit seconds to ~1 minute, no human input), the leader bot whispers or party-chats a concrete activity proposal that names a specific destination (quest name or dungeon name) and ends with a yes/no question. No travel, group invite, zone-in, or `accept *` is dispatched until the player answers "yes". A "no" answer produces a different proposal from the same activity menu.

**Acceptance Scenarios**:

1. **Given** the leader bot and the player are in the same world and the player has just logged in, **When** at most 60 seconds pass with no human chat, **Then** the leader bot sends exactly one proposal message that names a specific quest or dungeon and asks for a yes/no.
2. **Given** the leader bot has just proposed "Let's do Wailing Caverns", **When** the player replies "yes" / "ok" / "let's go" in party or whisper chat, **Then** the leader bot acknowledges and begins the existing playerbot action sequence to execute that activity (e.g. travel, group form, zone-in) within ~5 seconds.
3. **Given** the leader bot has just proposed an activity, **When** the player replies "no" / "not that" / "something else", **Then** the leader bot proposes a different activity from the two categories (quest, dungeon) without restarting from scratch, and does not retry the rejected option in the immediately next proposal.
4. **Given** the leader bot has just proposed an activity, **When** the player does not answer within a reasonable wait (~2 minutes), **Then** the leader bot sends one gentle nudge ("still there? want to do this or pick something else?") and continues to wait — it does **not** auto-approve or start executing.
5. **Given** the player gives any answer that is not a clear yes ("maybe", "later", "hold on"), **When** the leader bot processes it, **Then** the bot treats this as "not yet" — it waits and does not execute, but may follow up after a short delay.

### User Story 2 - Leader bot stays close to the player (Priority: P2)

The leader bot may begin moving toward an approved or candidate destination (e.g. walking to a quest giver, heading toward a dungeon portal), but it continuously checks the player's position. If the player falls more than a configured distance behind, the leader bot stops, turns around or waits, and pings the player in chat ("hold up, you coming? I'll wait"). The leader bot never wanders out of reasonable proximity of the player. If the player moves to a completely different zone, the leader bot abandons its current travel goal rather than running across the world.

**Why this priority**: The user's stated worry is "it doesn't go too far away". This is the safety guardrail that makes proactivity tolerable — without it, an enthusiastic leader bot would happily kite the player across continents. P2 because it only matters once P1 (proposals/approvals) is live and the bot actually moves on approved goals.

**Independent Test**: Player approves an activity. Leader bot begins moving. Player intentionally stops moving. Within a short window (~10-15 seconds), the leader bot stops, sends a chat message about waiting, and does not move further from the player until the player resumes following or gives a new instruction.

**Acceptance Scenarios**:

1. **Given** the leader bot is actively travelling to an approved destination, **When** the straight-line distance between leader bot and player exceeds a configured threshold (default ~60 yards), **Then** the leader bot stops moving and sends one chat line ("waiting on you", "you coming?", etc.) — and does not send a second one for at least 30 seconds.
2. **Given** the leader bot is waiting because the player fell behind, **When** the player closes the distance back below the threshold, **Then** the leader bot resumes travel toward the original destination without re-asking for approval.
3. **Given** the leader bot is travelling, **When** the player changes zones / continents / instance, **Then** the leader bot abandons the current travel goal and either teleports/follows-on-summon back to the player or stops and asks "where did you go? want to do something else here?".
4. **Given** there is no approved activity and the bot is idle near the player, **When** the player moves, **Then** the leader bot stays within follow range and never voluntarily moves more than the configured threshold away from the player.

---

### User Story 3 - Leader bot nudges an idle player (Priority: P3)

If the player is logged in but standing around doing nothing — not moving, not in combat, not in a conversation with the leader bot, not in an ongoing approved activity — the leader bot occasionally pings the player to suggest moving on ("hey, why are you standing? let's go, let's play"). These nudges are infrequent and not spammy: at most a small number per session, with mandatory cooldowns, and they are suppressed during obvious player intent signals (typing, looting, vendor window, etc., where detectable).

**Why this priority**: This is the "act alive" texture the user described. It depends on P1 (the bot already has a conversation cadence) and P2 (the bot is staying near the player), so it lands last. It is also the easiest slice to do badly — spamming a player every 30 seconds is worse than silence — so it ships behind the others.

**Independent Test**: Player logs in next to leader bot and stands still for several minutes without chatting or accepting any proposal. Leader bot sends a small, bounded number of idle nudges (e.g. no more than 3 in 10 minutes), each clearly differentiated from a fresh activity proposal, and goes silent if the player keeps ignoring them.

**Acceptance Scenarios**:

1. **Given** the player has been logged in and stationary for at least the configured idle threshold (default ~3 minutes), **When** there is no pending leader-bot proposal awaiting an answer, **Then** the leader bot sends one short idle nudge in chat that does not consume an "activity proposal" slot.
2. **Given** the leader bot has sent an idle nudge, **When** less than the idle-nudge cooldown (default ~5 minutes) has elapsed, **Then** the leader bot does not send another idle nudge — even if the player remains idle.
3. **Given** the leader bot has sent multiple idle nudges in a row with no response, **When** the player still does not engage, **Then** the leader bot stops nudging and waits silently for the player to act, up to the next session.
4. **Given** the player is mid-combat, in a vendor/loot/quest dialog (where detectable), or actively typing, **When** the idle threshold would otherwise fire, **Then** no idle nudge is sent.

---

### Edge Cases

- **Multiple gateway bots in range.** Only one bot acts as the leader-voice for the player at any time; the others stay silent on this proactive channel. Selection is deterministic per session (e.g. lowest-guid online gateway bot, or a configured designated leader) so the player doesn't get three simultaneous "let's quest!" lines.
- **Player approves but bot can't execute.** If the player says "yes" to a proposal that the bot then can't carry out (e.g. dungeon group can't be formed, quest giver unreachable, instance is on cooldown), the leader bot reports the blocker in chat in plain language and offers an alternative from the same menu — it does not silently fail.
- **Player gives a direct command instead of approving.** If the player ignores the proposal and instead types a command like "follow me" / "go grind" / a leader command, the bot honors the direct command (existing behavior) and treats it as cancelling the open proposal.
- **Server restart / bot relog.** Pending proposals do not survive a worldserver restart. After the bot comes back online, it starts a fresh proposal cycle as if the player had just logged in.
- **Player logs out.** The leader bot stops sending proactive proposals and nudges immediately. Proactivity is presence-gated to logged-in human presence (consistent with existing tactical-mode dormancy).
- **Rapid alternating "yes/no" by the player.** The bot must not loop or thrash: once an activity is approved and executing, a subsequent "no" cancels execution and returns the bot to the "propose next" state rather than restarting the just-cancelled one.
- **Player approves while bot is mid-proposal of the next one.** The latest proposal wins. The bot ignores any in-flight stale proposal.
- **Language / phrasing variance.** Player answers in casual language ("aight", "nah", "sure why not", "skip this one"). Yes/no/skip intent must be resolved on free-form text, not just exact-keyword matching.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The leader bot MUST initiate proactive activity proposals to the player on its own cadence, without requiring the player to chat first.
- **FR-002**: Each proposal MUST name a single concrete activity. The two **primary** v1 categories are **quest** and **dungeon**, each ending with a yes/no question in natural language. As a **fallback**, when the deterministic candidate selector (FR-006) finds no eligible primary candidate, the leader bot MAY propose a **soft zone suggestion** ("let's head to <zone>") instead of going silent — this fallback also ends with a yes/no but commits to less than a primary proposal (no specific quest/dungeon yet, the bot proposes a fresh primary once you arrive). Battleground is explicitly out of v1 scope.
- **FR-003**: The leader bot MUST NOT begin travelling to, group-inviting into, zoning into, or otherwise executing the proposed activity until the player explicitly approves it in chat. Approval is accepted from the channels the bot speaks on (party when grouped, whisper otherwise) and from the existing public-chat capture path.
- **FR-004**: The leader bot MUST recognize natural-language approval ("yes", "ok", "let's go", "do it", "sure", and reasonable variants) and rejection ("no", "skip", "not that", "something else", and reasonable variants) of an open proposal, distinguishing them from ambiguous / non-answers.
- **FR-005**: When a proposal is rejected, the leader bot MUST offer a different concrete activity from the two v1 categories without re-proposing the just-rejected option in the immediately next proposal.
- **FR-006**: The leader bot MUST select activities that are level-appropriate and faction-appropriate for the player's character at the time the proposal is generated. Candidate selection MUST be **deterministic** and rank candidates in this order: (1) **quests already in the player's quest log** (preferring quests with existing progress and/or objectives in the current zone), (2) **quests offered in the player's current zone** that the player is eligible to accept (level + faction + prerequisites), (3) **dungeons whose level range covers the player** and whose entrance is reachable from the current zone, (4) **fall back** to a "next level-appropriate zone for this faction/race" candidate if (1)-(3) are empty. The LLM phrases the proposal but does NOT choose the candidate; the candidate comes from this ranked query.
- **FR-007**: While travelling toward an approved destination, the leader bot MUST continuously check the player's position and MUST stop and wait (with a single chat line) when the player falls more than a configured distance behind (default ~60 yards, configurable).
- **FR-008**: The leader bot MUST NOT voluntarily move more than the configured proximity threshold from the player except while actively executing an approved travel goal — i.e. an idle leader bot stays near the player.
- **FR-009**: If the player changes zones/continents/instance while the leader bot is travelling, the leader bot MUST abandon the current travel goal and return to "near the player" state rather than continuing to its original destination.
- **FR-010**: If the player remains logged in but idle (stationary, not in combat, not in any UI interaction the system can detect, no active proposal) for at least a configured idle threshold (default ~3 minutes), the leader bot MUST send at most one short idle nudge in chat, then respect an idle-nudge cooldown (default ~5 minutes).
- **FR-011**: After a small bounded number of consecutive ignored idle nudges (e.g. 3 in a session), the leader bot MUST stop sending idle nudges for the remainder of the player's current session.
- **FR-012**: The leader bot MUST suppress all proactive proposals and nudges while the player is offline, consistent with existing tactical-mode presence gating.
- **FR-013**: When multiple gateway leader-capable bots are within range of the player, exactly one MUST act as the proactive voice for that player; the others MUST stay silent on the proactive proposal/nudge channel. The designated voice MUST be a bot **other than the target player itself** — the proposer and the target are distinct entities, so a leader-capable bot is never elected as its own voice (a degenerate proposal aimed at the proposer can never be answered, so it would just open → expire → reopen forever). This is automatic for a human target (a human is never leader-capable); it only bites when the bot fleet itself populates the FR-012 presence set, in which case the player's voice falls through to the next in-range leader bot, or to none when it is the only leader-capable bot in range. While a proposal or activity plan is in flight, the voice MUST stay **sticky** to the bot that owns it for as long as that bot remains in range — re-election to a different in-range bot happens only when no proposal/plan is in flight (or the owner leaves range), so a mid-activity voice handoff cannot strand the owning bot's `follow`/`stay` state or mis-attribute its proximity/abort audit rows to a different bot.
- **FR-014**: Direct player commands ("follow me", "stay", explicit leader-command verbs) MUST take precedence over the leader bot's current proposal; receiving a direct command MUST cancel any open proposal.
- **FR-015**: If the leader bot cannot execute an approved activity (group not formable, quest giver unreachable, instance on cooldown, etc.), it MUST surface the blocker to the player in chat in plain language and, on the next heartbeat after the abort settles, open a fresh proposal from the ranked candidate selector as the "alternative" — it MUST NOT silently fail, loop, or stall the proposal cycle.
- **FR-016**: Pending proposals MUST NOT persist across worldserver restarts or bot relogs; on coming back online, the leader bot MUST start a fresh proposal cycle.
- **FR-017**: All proactive chat lines (proposals, waiting messages, idle nudges) MUST be addressed to / aware of the specific player character by name, MUST read as natural conversation rather than command-shell output, and MUST be sent on the **party channel when the leader bot and player share a group**, otherwise via **whisper** directed at that player character. Proactive lines MUST NOT be routed to `/say` or `/yell`.
- **FR-018**: The feature MUST be controllable by a single configuration kill switch so the server operator can disable proactive leadership and revert to the existing reactive behavior. The kill switch MUST default to **OFF (disabled)** — the feature is opt-in, ensuring server operators get byte-identical baseline behavior unless they explicitly enable it.
- **FR-019**: Each proactive chat line MUST be subject to per-bot rate limiting consistent with the existing tactical ambient caps — specifically `Tactical.AmbientMinSpeechGapSec`, `Tactical.AmbientMinEmoteGapSec`, and `Tactical.AmbientMaxVisibleActionsPerMinute`. Proactive emits MUST route through (or count against) those existing counters, not just the new `Proactive.*Cooldown*Sec` keys, so that a misbehaving proactive loop cannot exceed the spam-prevention budget the rest of the module already enforces.
- **FR-020**: System MUST log every proactive proposal lifecycle event (proposal sent, approval received, rejection received, idle nudge sent, activity completed, activity aborted) to the **existing `mod_ollama_chat_gateway_audit` table** with a distinct `source_channel` label per event type (`proactive_proposal`, `proactive_approval`, `proactive_rejection`, `proactive_nudge`, `proactive_complete`, `proactive_abort`). The feature MUST NOT introduce a new audit schema; reuse and the existing `.ollama gateway prune` lifecycle apply.
- **FR-021**: When an approved activity completes (or is abandoned), the leader bot MUST automatically return to the proposal cycle and offer the next activity, rather than going silent. Completion is detected via a **hybrid** model:
  - **Primary — per-category server signals**: for quest, the quest turn-in event; for dungeon, zone-out from the instance map (or final-boss kill flag).
  - **Fallback — explicit player command**: the player may at any time say "done", "next", "what's next", or a reasonable variant in chat, and the bot MUST treat that as completion regardless of signal state.
  - **Timeout safety net**: if neither the primary signal nor the explicit fallback fires within a configurable hard timeout (default ~30 minutes from the activity's `executing` state), the bot MUST send one chat nudge ("are we done with this one?") and, if there is still no answer after a further short wait (~2 minutes), mark the Activity Plan as `aborted` and return to the proposal cycle.
- **FR-022**: Execution of the approved activity MUST be carried out using the **existing** playerbot strategy + leader-command primitives only — this feature MUST NOT introduce a new movement-planning or activity-execution engine, and MUST NOT require any new MCP tool/verb to ship v1. Specifically:
  - **Quest**: `accept *` / `talk *` for pickup and turn-in; existing travel/follow strategies for moving the bot toward the quest giver or objective; the player follows the leader bot.
  - **Dungeon**: existing travel/follow strategies to walk to the named instance portal + manual zone-in. Group formation uses existing party-invite verbs. **Random Dungeon Finder / LFG queue is NOT a v1 path** — "dungeon" in v1 means a specific named instance with a fixed entrance.
  - **Battleground**: out of v1 scope.
- **FR-023**: After a small bounded number of consecutive **expired** (silently-ignored) proposals in a single session (e.g. 5 in a session, configurable), the leader bot MUST stop opening new proposals for the remainder of the player's current session UNLESS the player produces an engagement signal (any chat, quest turn-in, or zone change). This is the proposal analogue of FR-011's idle-nudge self-silence: when the player has clearly stopped listening (auto-claim party, AFK, alt-tabbed for hours), proposing every ~10 minutes is chat-flood spam rather than leadership. The counter MUST be `uint16_t` per `(player, bot)` Cadence row, MUST increment on `Proposal::state` transition `open → expired`, MUST reset to zero on the engagement signals named above, and MUST NOT be incremented on explicit `reject` / `done` — those are answers, not silence.

### Key Entities *(include if feature involves data)*

- **Proposal**: An open suggestion from the leader bot to the player. Attributes: target player character, proposing bot, activity category (**quest** / **dungeon**), specific target (quest id+title or dungeon id+name), state (open / approved / rejected / expired / cancelled / executed), created-at, answered-at, expiry. At most one Proposal per (player, bot) is in `open` state at a time.
- **Activity Plan**: The concrete action sequence that an `approved` Proposal becomes — a series of existing playerbot commands or MCP tool calls (travel, accept, talk, party invite, zone-in). Lifecycle: queued → executing → completed / aborted.
- **Leader Mood / Cadence State**: Per-(player, bot) runtime state that controls when the next proactive line fires. Tracks: last-proposal-at, last-idle-nudge-at, consecutive-ignored-nudges, consecutive-expired-proposals (FR-023), currently-open-proposal-id. Reset on bot relog.
- **Designated Voice**: For a given player and a given set of in-range leader-capable bots, the one bot — **other than the player itself** (the proposer and the target are always distinct entities) — that owns proactive output for that player at this moment. Selection is deterministic and re-evaluated when the in-range set changes, but stays sticky to the owner of an in-flight proposal/plan (FR-013): the re-evaluation only changes the voice at lifecycle boundaries (no in-flight proposal) or when the incumbent leaves range.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: After the player logs in next to a configured leader bot, the player receives a first activity proposal in chat without typing anything, in ≤60 seconds on a warm server (model loaded, fleet online), and ≤120 seconds on a cold one.
- **SC-002**: At least 95% of approval-class answers ("yes", "ok", "let's go", "do it", and reasonable phrasings) and at least 95% of rejection-class answers ("no", "skip", "not that", "something else", and reasonable phrasings) are correctly classified by the intent layer — measured on a hand-labelled test set of ≥50 phrases per class.
- **SC-003**: Zero unapproved executions: across a representative play session (≥60 minutes, ≥10 proposals), no travel, group invite, zone-in, or `accept *`-style action is dispatched on behalf of an `open` or `rejected` proposal — only on `approved`.
- **SC-004**: The leader bot stays within the configured proximity threshold of the player at least 95% of the wall-clock time during a representative play session, excluding the short windows where it is actively travelling toward an approved destination.
- **SC-005**: Proactive chat volume (proposals + waiting messages + idle nudges combined) stays under the configured per-minute cap 100% of the time during a representative play session — there is no spam regression vs. existing tactical ambient.
- **SC-006**: Idle nudges stop on their own: after the player ignores nudges N times in a row in a single session (configurable, default 3), no further idle nudges are sent until the next session, measured across a multi-hour idle test.
- **SC-007**: Player-perceived "the bot is leading" rating in informal play-test feedback is positive — the player no longer feels they have to initiate or command, and does not feel spammed. (Qualitative, but verifiable per play session.)
- **SC-008**: Disabling the feature via the configured kill switch returns leader-bot chat behavior to pre-feature baseline within one config reload — measured by reproducing existing reactive-only behavior with the flag off.

## Assumptions

- The existing tactical / gateway companion stack remains the foundation: this feature adds a new proposal/approval loop on top of it, it does **not** replace mod-playerbots combat AI, the gateway reactive path, or the strategic escalation path. Combat, rotations, and threat continue to be owned by the playerbot engine.
- Proactivity is presence-gated to a whitelisted human being online, consistent with existing tactical-mode dormancy (`Tactical.HumanPresenceRequired = 1`). Bots do not propose activities into an empty world.
- The proactive proposal cadence borrows the existing tactical heartbeat / event-trigger mechanism rather than introducing a new clock — i.e. the tactical tick is the natural place to evaluate "is it time to propose?".
- Activity execution leans entirely on **existing** playerbot verbs and MCP leader-command primitives (`accept *`, `talk *`, `nc +grind`, dungeon/BG queue verbs, summon/follow, etc.). The feature does NOT include a new in-world movement planner.
- "Leader bot" in this spec means a gateway leader-capable bot (e.g. one of the Synthiq/OpenClaw squad: Claude / Clawd / Geek). It does not mean ad-hoc random playerbots; those continue to behave as today.
- Natural-language approval / rejection classification reuses the existing Ollama classifier path (`Gateway.OllamaClassifier`) rather than introducing a new LLM endpoint. No new model dependency.
- The two supported activity categories in v1 are **quest** and **dungeon**, plus a **soft zone-suggestion fallback** the bot uses when neither primary category has an eligible candidate (FR-002). **Battleground is explicitly out of v1 scope** (per Clarifications Q1, 2026-05-11 — user does not play BGs in the near term). Other categories (raid, arena, gathering, world boss, profession trips) are also out of scope for v1 but may be added later by extending the proposal menu — the proposal/approval mechanism is designed to be category-agnostic.
- The player is assumed to chat back in English; mixed-language input continues to be best-effort via the existing chat pipeline and is not a v1 success criterion.
- Persistent state (audit rows, mood state, etc.) reuses the existing module DB tables and lifecycle — specifically `mod_ollama_chat_gateway_audit` for all proposal lifecycle events (per Clarifications Q5, 2026-05-11). **No new SQL migration ships with this feature**; the existing `git_pull_module --import-sql` / `sql_import_dir` flow is not exercised. Open-proposal state is held in-memory (per the Leader Mood / Cadence State entity) and intentionally does NOT survive worldserver restarts (consistent with FR-016).
- This is a personal project; tracking lives in this repo (git branches, `docs/`, `docs/CHANGELOG.md`) per the project's `CLAUDE.md`. No corporate trackers, no Jira.
