# Architecture

### Source Layout (`src/`)

All source files follow the `mod-ollama-chat_<component>` naming convention:

| Component | Purpose |
|-----------|---------|
| `_main.cpp` | Entry point — registers all scripts (WorldScripts, PlayerScripts, event hooks) with AzerothCore's ScriptMgr |
| `_config.cpp/.h` | Global config variables (all `g_*` prefixed externs), loading from `.conf` file, personality/history DB loading |
| `_handler.cpp/.h` | Core chat handler — `PlayerBotChatHandler` (PlayerScript) intercepts player chat via `OnPlayerCanUseChat` hooks across all channel types. Two coordination-channel policies: (a) `g_BlacklistCommands` (playerbot verbs like "stop", "attack", "follow", "co", "nc") is skipped on whisper/party/raid/guild/officer channels so natural-language leader orders reach the gateway (kept for say/yell/general to avoid mob-name collisions). (b) Bots listed in `Gateway.MentionExemptBots` bypass the chance-roll in candidate selection, not just the later gating check — the leader bot therefore hears every coord-channel line without needing its name mentioned. Playerbots-command whispers (bare `co`, `nc`, `help`, `stats`, `stay`, `follow`, etc.) still get filtered before gateway dispatch to prevent auto-whisper loops from MultiBot-style client addons. |
| `_api.cpp/.h` | Ollama HTTP API integration — `QueryOllamaAPI()` sends prompts, `SubmitQuery()` returns `std::future<string>` for async |
| `_querymanager.cpp/.h` | Concurrency control — `QueryManager` queues API requests with configurable max concurrent queries |
| `_httpclient.cpp/.h` | HTTP client wrapper using cpp-httplib |
| `_llmwire.cpp/.h` | Wire-format adapter for the four fast LLM paths (tactical executor, gateway classifier, proactive intent, tick-gate). Picks Ollama `/api/generate` vs OpenAI `/chat/completions` shape **from the URL**, adds the `OpenAiCompat.ApiKey` bearer for the latter, and unwraps either envelope (surfacing provider `error.message` verbatim). This is what lets `Tactical.Url` / `OllamaClassifier.Url` point at DeepSeek without a rebuild. The high-reasoning gateway path and the disabled legacy chat path are deliberately not routed through it. Standalone-provable with a stubbed `config.h` (44-check harness, 2026-09-20). |
| `_jev.cpp/.h` + `_jev_core.h` | **jev decision tier** (2026-09-21) — TypeSafe's System One model in front of the decision-shaped fast paths: gateway classifier (A), proactive intent (C), tick-gate (D), planner veto (E). State + typed questions in, calibrated `choice`/`noul`/`score` answers out; no text. Sits *above* LlmWire: jev first → the unchanged LlmWire/DeepSeek call → deterministic code, under one absolute deadline per chain, with a jev-side breaker and a keep-alive proxy-aware client pool. `_jev_core.h` is dependency-free (builders, parser, breaker, deadline arithmetic) so `tests/jev/harness_*.cpp` compile it with bare `g++`. Question wording lives in `prompts/jev_questions.json`; option sets always come from the live allowlists. Adds the `backend` audit column via startup self-migration. Tactical executor (B) is deliberately NOT on jev yet (PR 2). See [docs/jev.md](../jev.md). |
| `_events.cpp/.h` | Gameplay event hooks that record recent event context for Tactical Ambient Mode |
| `_personality.cpp/.h` | Bot personality system — assignment, lookup, prompt modification per personality type |
| `_sentiment.cpp/.h` | Bot-player sentiment tracking — tracks relationship sentiment (0.0-1.0) between bots and players, persisted to DB |
| `_rag.cpp/.h` | RAG system — retrieves relevant WoW knowledge from JSON files in `data/rag/` to enrich prompts |
| `_gateway.cpp/.h` | Gateway agent bot — routes designated bots to an external OpenAI-compatible API (OpenClaw or Synthiq) instead of Ollama. See `docs/gateway.md` for full feature reference (hardening, streaming, per-agent presets, channel expansion, JSON config, tool-use bridge, audit). Two cost-shaping layers added April 2026: (1) `BuildGatewaySystemPromptEx` now embeds a **BOT STATE SNAPSHOT** (HP, zone, group roster with human/bot/you tags) + a **LEADER PLAYBOOK** that maps ~20 natural-language orders ("stop", "tanks pull", "DPS focus X", "gear up Geek", "mark skull", "invite X") to explicit MCP calls with botGuid pre-filled. (2) `TryGatewayIntentClassify` — cheap-path Ollama classifier: before firing the paid Synthiq call the handler runs a short classification prompt on the fast local classifier model; on confidence ≥ `Gateway.OllamaClassifier.MinConfidence` (default 0.8) and the action is in the safe-action allowlist, the tool is dispatched in-process and a pre-canned ack is returned, bypassing Synthiq entirely. Expected ~80% cost cut on canonical gameplay commands; nuanced/conversational messages still escalate to Sonnet. Uses Gateway.OllamaClassifier.{Url,Model,TimeoutMs,NumCtx}, inheriting Tactical.Url/Tactical.Model when endpoint/model are empty. Gated by `Gateway.OllamaClassifier.Enable` (default 1). |
| `_tools.cpp/.h` | Transport-agnostic tool registry. **59 tools** (added 8 ops-api proxy tools — `ops_status`, `ops_logs_tail`, `ops_files_{list,read,search}`, `ops_audit_{gateway,tactical,summary}` — each a thin GET to `wow-ops-api`; `bot_set_raid_target_icon` paints actual raid icons via `Group::SetTargetIcon`, distinct from `bot_rti` which only sets the bot's assist preference; `bot_rti` accepts `icon="none"` to clear that preference). Other invariants: (a) every dispatched playerbot verb is automatically prefixed with `sPlayerbotAIConfig.commandPrefix` ("!" by default) — bare commands silently no-op at `PlayerbotAI.cpp:935`; (b) `DispatchLeaderCommand` passes the LEADER'S MASTER (the human via AutoClaim) as `fromPlayer`, not the leader bot itself — peer bots fail `PLAYERBOT_SECURITY_INVITE` and `HandleCommand` returns silently; (c) `Tool_LeaderCommandAll` rewrites bare `accept`→`accept *` and `talk`→`talk *` (playerbot's `AcceptQuestAction` requires a quest_id or `*`, otherwise no-op); (d) `Tool_LeaderCommandAll` substitutes `attack my target`/bare `attack` with the leader's master's selected unit name before broadcasting (`AttackMyTargetAction::GetMaster()` reads `PlayerbotAI::master` which AutoClaim re-homing doesn't reliably wire on subordinates); (e) `ResolveLeaderTargets` includes the leader itself, so `leader_command_all` and `emergency_stop` actually hit the leader on inclusive verbs (accept, drink, follow, attack, stay); (f) `Tool_BotFollow` skips with ok-noop when bot is <10y from the whisperer/master and enforces a 90s per-bot dedup gap so playerbot's `FollowAction::TellMaster("Following X")` doesn't spam chat. Counts updated to 27 read-only + 23 self-actions + 5 leader + 4 misc. The previous tool catalog still applies; the gates and quest/combat/gear/progression/strategy/raid/config-edit/ops-api-proxy groupings below are unchanged. |
| `_tools.cpp/.h` (legacy catalog) | 27 read-only (`get_bot_state`, `get_player_state`, `get_zone_info`, `get_player_gear`, `get_player_quests`, `get_nearby_players`, `get_nearby_creatures`, `get_nearby_gameobjects`, `get_group`, `get_target`, `get_inventory`, `query_world_db_lookup`, `get_bot_roster_by_account`, `get_fleet_status`, `bot_list_strategies`, `config_list_files`, `config_get_file`, `config_get_value`, `ops_module_status`, plus 8 ops-api proxies — `ops_status`, `ops_logs_tail`, `ops_files_list`, `ops_files_read`, `ops_files_search`, `ops_audit_gateway`, `ops_audit_tactical`, `ops_audit_summary` — gated behind `Ops.Enable=1`, see `docs/ops-api.md` §MCP tools). Autonomous fleet runbook lives at `docs/autonomous-bots.md`. `emergency_stop` is a dedicated panic-button wrapper over `leader_command_all("stay")`, 1 write (`whisper_player`), 23 self-actions dispatched via `PlayerbotAI::HandleCommand` (`bot_follow`, `bot_stay`, `bot_emote`, `bot_invite_to_group`, `bot_use_item`, `bot_cast`, `bot_sell_junk`, `bot_accept_quest`, `bot_abandon_quest`, `bot_turn_in_quest`, `bot_attack_target`, `bot_stop_combat`, `bot_revive`, `bot_autogear`, `bot_equip_item`, `bot_unequip_item`, `bot_maintenance`, `bot_train_spells`, `bot_set_strategy`, `bot_reset_ai`, `bot_rti`, `bot_disperse`, `bot_roll`) gated behind `Mcp.AllowActionTools=1`, and 5 leader tools (`leader_list_targets`, `leader_command`, `leader_command_all`, `leader_get_command_help`, `leader_admin_command`) gated behind `Mcp.Leader.Enable=1` + per-bot allowlist (`Mcp.Leader.BotGUIDs`). `leader_command*` issue playerbot text commands at OTHER bots in scope (group/nearby/owner/all); `leader_admin_command` runs `.playerbots bot add/remove/addclass/list` via the **leader's master WorldSession** — `.playerbots bot` rejects bot-issued calls (`PlayerbotsMgr::GetPlayerbotMgr` returns null for bots), so the tool dispatches on behalf of the human owner. Tool availability is gated separately by `Mcp.Leader.AllowAdminCommands=1`; at runtime the master must also be online and in-world. Quest tools (`bot_accept_quest` / `bot_abandon_quest` / `bot_turn_in_quest` / `bot_choose_quest_reward`) wrap playerbot `accept`/`drop`/`talk`/`r` verbs and close the quest-progression loop for autonomous play (discover via `get_nearby_creatures` → accept → complete → turn in → pick choice reward). `bot_choose_quest_reward` (item_id only — the upstream verbs parse an item LINK, never a name) selects the right item from a multi-reward turn-in dialog so the agent can pair role-appropriate rewards with the bot (spirit cloak for healers, etc.). Combat lifecycle tools (`bot_attack_target` / `bot_stop_combat` / `bot_revive`) wrap `attack` / `reset` / `release`+`revive` verbs — engage → disengage → recover — giving the agent a self-driven combat loop without needing leader scaffolding. Gear lifecycle tools (`bot_autogear` / `bot_equip_item` / `bot_unequip_item` / `bot_destroy_item`) wrap `autogear` / `e` / `ue` / `destroy` verbs for slot-level or one-shot gear management; `bot_destroy_item` reclaims bag slots when items can't be sold (BoP greens) or banked. Progression tools (`bot_maintenance` / `bot_train_spells` / `bot_set_home`) wrap `maintenance` / `trainer learn` / `home` — close the "just levelled up, now prep for next pull" loop so the agent can autonomously keep spells/skills/repair/consumables current without a human prepping bots; `bot_set_home` rebinds the hearthstone target when relocating a fleet to a new home city. Strategy tools (`bot_list_strategies` / `bot_set_strategy` / `bot_reset_ai`) wrap `co` / `nc` / `reset botAI` verbs — the persistent-mode layer that drives *how* a bot decides to act on every combat/non-combat tick (role, AOE handling, threat, pet stances, druid forms, raid-specific overrides); list reads engine state directly so the agent can diff before mutating, reset reverts to class/level/role defaults when experimentation leaves a bot misconfigured. Raid coordination tools (`bot_rti` / `bot_disperse` / `bot_roll`) wrap `rti` / `disperse` / `roll` verbs — focus-fire / CC marking, AOE-spread enforcement, and last-chance loot rolls for raid encounter coordination. Config-edit tools (`config_list_files` / `config_get_file` / `config_get_value` / `config_set_value` / `config_reload`) let the agent read and edit allowlisted `.conf` files in place with atomic write-tmp+rename, timestamped backup, per-file key allowlist, deny-pattern sweep (always protects `*Token*`/`*Password*`/`*DatabaseInfo*` etc.), and audit. `config_reload` reloads `mod_ollama_chat` in-process (`ReloadOllamaChatRuntime()`) or dispatches `.playerbots bot reload` / `.reload config` via `Mcp.ConfigEdit.ReloadAdminSessionGuid`'s session (Overlord). Gated behind `Mcp.ConfigEdit.Enable=1` + for writes `Mcp.AllowActionTools=1`. Full runbook: `docs/autonomous-bots.md` §Self-reconfiguration. |
| `_opsapi.cpp/.h` | HTTP-GET proxy helper backing the 8 ops-api MCP tools. `CallOpsApi(path, params)` builds `g_OpsUrl + path + ?...`, percent-encodes query values, attaches `Authorization: Bearer g_OpsBearerToken`, calls `OllamaHttpClient::Get`, and returns the parsed JSON. Errors (transport / non-2xx / non-JSON) propagate as `{"error":"opsapi: ..."}` with the upstream status + body snippet so MCP clients see what actually failed. Master gate `Ops.Enable=1`. |

| `_proactive.cpp/.h` | Feature 002 — proactive leader bot. Inverts the leader/follower dynamic: a designated voice (lowest-guid election or `Proactive.PreferredVoiceGuid` override) opens with a concrete proposal within ~15-60s of player login, waits for natural-language approval (C++-side string-match classifier — no LLM round-trip for yes/no/done), dispatches `!follow` on approve, auto-recycles on quest turn-in / explicit "done" / 30-min timeout. Proximity guardrails: 3D `GetDistance` against `Proactive.ProximityYards`, pauses travel + emits one `proximity_warn`, resumes silently on re-entry; zone/map change aborts the plan. ### Key Data Flow

**Legacy direct local Ollama chat path:**
Removed. Player chat no longer falls back to local prompt generation or `SubmitQuery()`.
Player chat reaches gateway/classifier bots only; proactive local behavior lives
in Tactical Ambient Mode. Old random/event local-Ollama config keys are parsed
as deprecated no-ops for one release.

**Gateway agent path (whisper by default; configurable via `AllowedChannels`):**
1. Player chats on a channel in `AllowedChannels` and targets a bot whose GUID is in `g_GatewayBotGUIDSet`
2. Gating layers (AND-combined):
   - Whisper: passes if TriggerKeyword empty OR present in message
   - Party/raid/guild/officer: same TriggerKeyword logic AND, when `PrivateChannelMentionRequired=1` (default), the bot's own name must appear in the message — prevents whole-party-chat spam when keyword is empty. Bots whose names are listed in `MentionExemptBots` (csv, case-insensitive) skip the mention check and respond to any party line
   - Public (say/yell/general): `PublicChannelMode` = keyword / mention / both
3. Cooldown + concurrency cap check; spawn detached thread for the API call
4. Query path depends on `gatewayType` + global flags:
   - `openclaw` + streaming off: `QueryGatewayAPI()` (buffered)
   - `openclaw` + streaming on: `QueryGatewayAPIStreaming()` (SSE, sentence-boundary whispers)
   - `synthiq` + `EnableToolUse=1`: `QueryGatewayAPIWithTools()` (OpenAI tools[] + tool_call loop)
5. Per-bot overrides (`g_GatewayBotConfigs`, with optional `headers` + `gatewayType` fields) resolve URL/token/model/headers. **Synthiq-routed bots ignore the request-body `model` field** (verified against the gateway). To switch models on Synthiq, send the `x-synthiq-model-override` header per-bot via `BotOverridesJson` `headers` map. The full per-bot config goes through `OllamaChat.Gateway.BotOverridesJsonFile` (file path) because AC's `Config.cpp:327` strips ALL `"` characters from inline values, breaking embedded JSON. Priority: `BotOverridesJsonFile` > inline `BotOverridesJson` > legacy `BotOverrides` colon string.
6. Optional `x-synthiq-session-key` header for warm-session reuse; optional personality-prompt merge; optional Cyrillic language hint
7. Response is chunked (sentence-aware) and sent to the matching channel (`Whisper` / `SayToParty` / `SayToGuild` / `Say` / `Yell`)
8. Audit row written to `mod_ollama_chat_gateway_audit` when `EnableAudit=1`
9. Gateway errors/empty responses are logged and audited; the legacy local
   Ollama fallback keys are deprecated no-ops.

`OllamaChat.DisableOllamaResponses` is now a deprecated direct-chat no-op. Use
`OllamaChat.Tactical.Enable` and `OllamaChat.Tactical.AmbientEnable` to control
local Ollama companion behavior.

### Configuration

- **Runtime config**: `conf/mod_ollama_chat.conf.dist` — all settings are `OllamaChat.*` keys under `[worldserver]`
- **Hot reload**: `.ollama reload` GM command or `ollama reload` from server console (also reloads player prefs, resets gateway stats + cooldowns)
- **Personalities**: SQL files in `data/sql/characters/updates/` (format: `YYYY_MM_DD_personality_pack_NAME.sql`)
- **RAG data**: JSON files in `data/rag/` containing WoW knowledge (zones, classes, items, quests, etc.)
- **Gateway docs**: `docs/gateway.md` is the authoritative feature/config reference. `docs/CHANGELOG.md` tracks behavior changes per release.

### DB tables (acore_characters)

- `mod_ollama_chat_personality`, `mod_ollama_chat_personality_templates` — bot personalities
- `mod_ollama_chat_history` — conversation history (shared between Ollama and gateway paths)
- `mod_ollama_chat_bot_player_sentiments` — relationship sentiment
- `mod_ollama_chat_optouts` — account-wide opt-out (player-facing via `.ollama optout`)
- `mod_ollama_chat_bot_mutes` — per-(account, bot) mute (via `.ollama mute <BotName>`)
- `mod_ollama_chat_gateway_audit` — one row per gateway call when `EnableAudit=1`; pruned by `AuditRetentionDays`

### Concurrency Model

Gateway, classifier, and tactical LLM calls are asynchronous. The legacy
`SubmitQuery()`/`QueryManager` direct-chat path remains in the source for
compatibility but is not used by ordinary player-chat routing.

### Global State

All configuration is stored in `g_*` global variables (declared as externs in `_config.h`). Conversation history and sentiment data use `std::unordered_map` with dedicated `std::mutex` guards. Periodic save intervals flush data to the database.
